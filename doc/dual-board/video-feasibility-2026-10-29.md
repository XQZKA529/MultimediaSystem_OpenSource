# 视频功能的资源可行性与取删方案（2026-10-29）

目标：在**不损失赛题基础要求与全部 5 项拓展要求**的前提下，把视频播放塞进当前双板工程，视频规格取 480p 或 360p、15 fps 或 30 fps。

本文所有数字标注来源。**"实测"** 指 `build/avi-v1/` 中已存在的 AVI 视频候选的真实综合/布线报告；**"换算"** 指用 LE→Slice 比例换算的估算值；**"待验证"** 指未经布线的推断。

> **修订（2026-10-29 13:15）**：需求方明确 **DDC/CI 可删、亮度调节必须保留、应急接管必须保留**（应急是针对赛题应用场景设计的，属于必须功能）。
> §6 的"删应急"方案作废，改为 §10 的两条最小改动路线。结论也随之变化：**在 15 fps 以内，可以不删任何功能、不动 BRAM，直接塞进去。**

---

## 1. 结论摘要

| 问题 | 结论 |
|---|---|
| 视频通路本身占多少资源 | render 侧净增 **约 50–350 Slice + 1–2 BRAM32K**（两次构建优化状态不同，无法精确分离）；实测含视频的完整布线 9313 Slice，**比当前 9593 还低 280** |
| 真正的瓶颈在哪 | **不在 render，在 media**。avi_v10 实测打包 5261/4900 M-Slice，等价 10522/9800，**超 722** |
| 删功能能解决吗 | **在 media 上解决不了**。media 可删的只剩应急 148 Slice（台标在那版构建里已扣过），缺口 722 补不上 1/5。render 侧则根本不需要靠删功能换面积 |
| 那怎么办 | 把通用 AVI 容器解析换成**固定布局帧流**，media 净增从 ≈986 降到 ≈300–400，配合删除台标/应急即可塞下 |
| 带宽够不够 | 15 fps 用 640×360 24bpp（10.4 MB/s）可行；**30 fps 只能到 320×240~480×300 级别**，或改用 16bpp 且把 SD 拉到 50 MHz |
| 最大风险 | render 视频读口抢 SDRAM 读通道，实测 Setup **−1.128 ns**；删功能只能缓解，必须改仲裁 |

一句话：**视频不缺逻辑，缺的是 SD 带宽和 media 的面积；而 media 的面积应该从"别做通用 AVI 解析"里省，不是从删演示功能里省。**

## 2. 现状基线

| 指标 | media | render |
|---|---:|---:|
| Slice | 9,536 / 9,800（优化后放置） | 9,593 / 9,800（已布线） |
| LUT | 16,844 | 16,886 |
| BRAM9K | 58 / 64 | **64 / 64（满）** |
| BRAM32K | 1 / 16 | **16 / 16（满）** |
| DSP | 26–28 / 29 | **29 / 29（满）** |
| Setup WNS | −0.522 ns（旧源码完整布线，未签核） | +0.052 ns（零违例） |
| 剩余 Slice | **264** | **207** |

两板的资源结构完全不同：

- **render 是 BRAM/DSP 全满**。任何需要行缓存、字库、深 FIFO 的视频结构，都必须先腾 BRAM32K。
- **media 是 LUT/Slice 紧、BRAM 富余**（6 个 BRAM9K + 15 个 BRAM32K 空闲）。视频缓存放 media 侧没有存储障碍，卡的是逻辑面积。

## 3. 已有实现与它的真实代价

`build/avi-v1/` 中已有一套完整的 320×240 AVI 视频方案（`avi_v10` media + `avi_v11` render），含 20 余个已通过用例，状态为 `incomplete: media physical capacity and qualification remain unsatisfied`。

### 3.1 实测资源

| 板 | LUT | Slice / 等价 | BRAM9K | BRAM32K | DSP | Setup WNS |
|---|---:|---:|---:|---:|---:|---:|
| media（avi_v10） | 19,103（+2,259 over 16,844） | 5261 M-Slice → 等价 10,522 / 9,800 | 63 | 15 | 28 | 布线未完成 |
| render（avi_v11） | — | 9,313 / 9,800 | 60 | 14 | 29 | **−1.128 ns / TNS −41.884** |

两次构建都**已经删掉台标**（render 去掉 `image_overlay_64`，media 去掉 `sd_overlay_controller`）——也就是说上面的数字是在"已经牺牲台标"之后取得的。

### 3.2 它的设计为什么省

从 RTL 直接读出的结构，这几条决定了视频不必重写帧缓存事务：

1. **视频不进 720p 双帧缓存**。帧数据写在 SDRAM 尾部剩余区：`0x151800` 与 `0x15F900` 两块，每块 57,600 字（240 行 × 240 字），共占 115,200 字。两帧 720p 缓冲占到 `0x1517FF`，尾部还剩 714,752 字，装得下。
2. **不做整帧事务**。没有 `IMG_BEGIN/END/PRESENTED`、没有整帧 CRC、没有转场双读。`avi_scanout` 按"一行 240 字"向 SDRAM 提请求，`read_urgent` 抢在显示读的前一行位置插入，写完一行立刻可用。
3. **不做缩放器**。3× 行列重复把 320×240 直接铺成 960×720，左右各留 160 像素黑边。整条通路只有一个 BRAM32K 装"两行打包数据"和一个 8 态预取器。
4. **音画同步已经做了**。帧 PTS = `frame × 1920` 样本（48 kHz / 25 fps），与 `audio_position` 比对：落后超过 2720 样本置失败，超过 800 样本拒绝提交。这正好补上协议 v1.14 里"不承诺跨板时间戳同步"的空白。

所以**赛题里"多源信息融合 / 音画同步 / 低延迟显示"的叙事是现成的**，不需要新造。

### 3.3 代价集中在哪里

media 侧新增三个模块：

| 模块 | 行数 | 作用 | 评价 |
|---|---:|---|---|
| `avi_file_index.v` | 240 | 通用 AVI 1.0 RIFF 递归走查（15 态、`hdrl/strl/movi` 嵌套、4 级 rec 栈占 1 个 BRAM32K、双流识别） | **这是超标主因**，能力远超演示所需 |
| `avi_player.v` | 232 | 三游标调度（index / PCM / video）+ WAV 抢占与恢复（`freeze_wav`/`restore_*`） | 音频交织带来的复杂度 |
| `avi_context_word.v` | 48 | 用 1 个 BRAM32K 保存 32 位上下文 | 纯浪费，改寄存器即可 |

`seam_media` 本身 2,023 LUT、`seam_render` 2,011 LUT 也值得注意——一个打包/解包器吃掉两板各 12% 的 LUT，是另一块可挖的空间。

## 4. 规格与带宽核算

### 4.1 三处带宽，只有 SD 是墙

视频走独立 SDRAM 区、按行取数，**链路只传源分辨率字节**（不像图片固定 2.76 MB/帧），所以：

| 通道 | 容量 | 30 fps / 640×360 16bpp 占用 |
|---|---:|---:|
| SD（4bit @25 MHz） | **12.28 MB/s**（见 §4.3 逐拍核算），实测锚点 12.5 量级 | **13.8 MB/s — 卡死** |
| 千兆链路 | ~90 MB/s 可用 | 13.8 MB/s — 15% 占用，无压力 |
| SDRAM（100 MHz×32） | 400 MB/s 峰值 | 写入 13.8 + 显示读 168 ≈ 46%，安全 |

### 4.3 SD 速率到底是多少（2026-10-29 补正）

本文件早期版本写"实测按 80% ≈ 10 MB/s"，属保守估计，**已作废**。逐拍核算如下：

`media/rtl/sd/sdio_core.v` 头部注释给出单块时序——512 字节 = **1042 个 SD 时钟**：

```
1 个时钟    起始位（不承载数据）
1024 个时钟 512 字节，每时钟一个 nibble（4 bit）
16 个时钟   DAT0..3 各自的 CRC16
1 个时钟    结束位
```

512 B / 1042 clk = 0.4913 B/clk，× 25 MHz = **12.28 MB/s（98.2% 利用率）**。

实测锚点：`media_core.v` 注释记录了 2026-09-28 的实测——单张 1280×720 BMP 加载 **0.22 s**。该文件 2,764,854 字节，对应 12.6 MB/s 量级，与上面的核算一致；同时也说明**整条图片通路已经是 SD 带宽瓶颈**，缩放与打包还有余量。

突发粒度的影响：

| 突发 | 每块额外开销 | 有效速率 |
|---|---|---:|
| 64 扇区（CMD18） | 命令+响应约 96 clk / 66,688 clk | ≈ 12.25 MB/s |
| 4 扇区（图像通道限值） | ≈ 2.5% | ≈ 12.0 MB/s |
| 1 扇区（音频通道，CMD17） | ≈ 9% | ≈ 11.2 MB/s |

因此**可用值取 11.5–12.2 MB/s**。§4.2 表中的 △ 判据相应从"超 80%"改为"超 95%"。

另：`SD_CLK_DIV_HS=1`（50 MHz → 25 MB/s）**不是改个参数就能开**。源码注释记录了放弃原因：`SD_CLK` 输出路径完全不进 STA、采样相位无可约束余量，利用率 91.5% 时 `sd_card_clk` 域已有 14 个 setup + 7 个 hold 违例，50 MHz 下位周期仅 20 ns，这点未受控偏移直接把采样点挤出位边界；且 `SAMPLE_DLY` 旋钮在 `DIV=1` 时失效。当前利用率 95%+，这条路要走必须先给 `SD_CLK` 输出加约束并把利用率压回 ≤85%，属于板级/STA 专项，不能当作备选捷径。

### 4.2 可行组合

| 源格式 | 每帧字节 | 15 fps | 20 fps | 25 fps | 30 fps |
|---|---:|---:|---:|---:|---:|
| 640×480 24bpp | 921,600 | 13.8 ✗ | 18.4 ✗ | ✗ | ✗ |
| 640×480 16bpp | 614,400 | 9.2 ✓ | 12.3 △ | ✗ | ✗ |
| 640×360 24bpp | 691,200 | **10.4 △** | 13.8 ✗ | ✗ | ✗ |
| 640×360 16bpp | 460,800 | 6.9 ✓ | 9.2 ✓ | **11.5 △** | 13.8 ✗ |
| 480×360 24bpp | 518,400 | 7.8 ✓ | 10.4 △ | 13.0 ✗ | ✗ |
| 320×240 24bpp | 230,400 | 3.5 ✓ | 4.6 ✓ | 5.8 ✓ | **6.9 ✓** |

✓ 有余量　△ 超 95% 可用带宽（12.2 MB/s），风险高　✗ 超 12.28 MB/s 硬上限

**按用户目标给出的三个可用点：**

| 方案 | 规格 | SD 占用 | 显示方式 | 需新增能力 |
|---|---|---|---|---|
| A｜15 fps 首选 | 640×360 24bpp | 10.4 MB/s（83%） | 2× 重复 → 1280×720 满屏 | 重复系数 3→2 参数化；无格式改动 |
| B｜30 fps 唯一可行 | 320×240 24bpp | 6.9 MB/s（55%） | 3× 重复 → 960×720 + 黑边 | 无需改动（现成实现就是这档） |
| C｜30 fps 高画质 | 640×360 16bpp | 13.8 ✗ | 2× → 满屏 | 需 16bpp 解包 **且** SD 切 50 MHz（`SD_CLK_DIV_HS=1` 已有代码，但 `SAMPLE_DLY` 在该分频失效，要先重调采样点） |

480p（640×480）在 15 fps 下**必须 16bpp** 才进得去（9.2 MB/s）；24bpp 要 13.8 MB/s，超理论值。且 640×480 → 720p 是 1.5× 非整数放大，需要 `2,1,2,1` 行对或直接 1× 居中窗口，视觉上不如 360p 的 2× 满屏。

> 注：现有 `avi_scanout` 的重复系数、240 行行缓冲、`2720/800` 样本阈值、`frame×1920` 帧周期全部是 **25 fps / 320×240 硬编码**。换任一规格都要同步重标定这四处，否则音画同步判据失效。

## 5. 资源缺口核算

### 5.1 render：面积不是问题

avi_v11 在**加了视频、删了台标与饱和度**的情况下做到 9,313 Slice，比当前 9,593 低 280。把删掉的两项按 LE 折算补回（83+520 LE ≈ 320 Slice），也只是与当前持平。

也就是说：**render 加视频不需要靠删功能来换面积**。视频扫描通路本身很薄（一个 BRAM32K 行缓冲 + 8 态预取器 + 一个请求邮箱），代价在时序而不在面积。

**render 的真实问题是 Setup −1.128 ns**，见 §7。

### 5.2 media：缺 722，删功能基本补不上

| 项 | Slice |
|---|---:|
| 视频净增（AVI 原样；该数字取自"已删台标"的构建，故视频原始新增约 1,197） | ≈ 986 |
| 现有余量 | +264 |
| 可删：应急 `emergency_media_controller` 281 LE | +148 |
| 台标 `sd_overlay_controller` 401 LE | 已在上面的 986 里扣过，**不能再算一次** |
| **缺口** | **≈ −574** |

media 的模块几乎全部对应赛题必需项（SDIO、FAT32、BMP 解析与缩放、WAV、字幕、文件浏览器、链路），**可删的功能到此为止，只剩 148 Slice**。574 的缺口只能从"实现方式"里省，见 §6.2。这也是本文最核心的判断：**在 media 上继续找功能删是死路，必须换实现。**

### 6.1 按可回收量与赛题影响排序（LE 为实测，Slice 为换算）

**推荐组合：render 删 1+2+4（应急 + DDC/CI + 诊断条）**，回收 ≈ 985 Slice（1,130+546+176 = 1,852 LE）、2 块 BRAM9K、3 个 DSP；**media 删应急** 148 Slice。

台标（第 3 项）作为 **BRAM32K 的备用额度**保留：只有当视频行缓冲从 320 宽改到 640 宽、需要第二块 BRAM32K 时才砍。它在 media 那版构建里已经扣过，不能再当面积算第二遍。

这个组合**不动任何一条赛中明写的功能**，只牺牲"应急接管 + 显示器背光调节 + 诊断条"这三个赛题外/弱关联项。

### 6.2 不建议走"再删功能"的路

删到第 5 项以后，动的是转场种类、频谱密度这类**评分直接看得见**的东西，性价比远低于下面两条：

- **把通用 AVI 解析换成固定布局帧流。** 约定离线工具产出：32 字节头（宽、高、帧字节数、帧数、fps、色深）+ 连续帧数据。`avi_file_index` 整块（240 行、4 级 rec 栈、1 个 BRAM32K）与 `avi_context_word` 都不再需要，`avi_player` 的三游标退化成单游标 + 帧偏移递推。预估 media 净增从 ≈986 降到 **≈300–400**，配现有余量 264 + 删应急 148 即可塞下（9,536 + 400 − 148 ≈ 9,788）。**这是本文最重要的建议**：省的是"通用性"，不是"演示能力"。
- **`seam` 重构。** `seam_media` 2,023 LUT / `seam_render` 2,011 LUT，一个打包解包器吃掉两板各约 12% LUT。仓库里已有 `media_fit_packermerge34`、`media_fit_txshare52` 等约 160 个面积候选，说明这条路已经在走。若能把两侧各压 30%，等于凭空多出 ≈300 Slice/板，且零功能损失。

## 7. 时序风险

### 7.1 render：视频读口抢 SDRAM 是 −1.128 ns 的根因

`avi_scanout` 与显示读共用 `frm_app_rd_en/addr`，靠 `avi_mem_mode` 切换，并靠 `read_urgent` 插队。这条路径上串了：视频域请求 toggle → 双级同步 → 模式切换 → 地址选择 → SDRAM 读使能。而 SDRAM 读使能本来就是全设计扇出最高、最敏感的路径之一。

三个可动的手段（按性价比）：

1. 视频行请求**提前一行发起**，用现有 `request_row=source_row+1` 机制预留更长的窗口，让 `sdr_busy` 判断脱离关键路径。改动小。
2. 给 `avi_mem_mode` 加一级寄存器，把跨域比较从使能路径移走——这与 2026-10-25 修 `frame_fifo_read_dual` 的手法同源（`App_rd_en` 寄存化）。
3. 视频读走**独立突发**（固定 240 字、不可打断），与显示读在同一仲裁器里排优先级，避免每字切换。

删掉应急/诊断/DDC 会降低拥塞、对时序有正贡献，但**不能替代上述结构修改**：−1.128 ns 是路径问题，不是密度问题。

### 7.2 media：先签核，再加功能

media 当前 WNS −0.522 ns、213 个违例端点，还没关。在未闭合的基础上叠 300–1000 Slice 的新逻辑，等于在流沙上盖楼。**先关时序是这条路的硬前置条件**，而且它与视频无关，本来就该做。

## 8. 推荐落地路线

| 步 | 内容 | 门槛 |
|---|---|---|
| 0 | media 时序闭合（单独任务，与视频无关） | 完整布线 Setup/Hold 零违例，Slot ≤ 9,800 |
| 1 | render 删应急 + 诊断横幅 + DDC/CI，台标暂留（等确认行缓冲需求再定） | 回收 ≈ 985 Slice（1,852 LE）、2 块 BRAM9K、3 DSP；重新布线仍零违例 |
| 2 | media 换固定布局帧流容器（不做通用 AVI），删应急 | 净增 ≤ 400 Slice，放置 ≤ 9,700 |
| 3 | render 接入 `avi_scanout`，先跑 320×240@25fps（现成实现，验证通路） | 音画同步判据生效；Setup 转正 |
| 4 | 参数化到目标规格：640×360@15fps（2× 满屏）或 480×360@20fps | 重标定重复系数、行缓冲字数、PTS 阈值；实板连续 30 分钟无丢帧 |
| 5 | 补离线工具：视频 → 定长帧流（Python，按 `tools/convert_fpga_bmp.py` 风格） | 与 `sim/bmp_scale_reference.py` 同级的逐像素模型比对 |

第 3 步是关键决策点：**先用现成的 320×240@25fps 验证整条通路和音画同步**，确认无误后再改规格。如果一上来就改 640×360，行缓冲、重复系数、PTS 三处同时动，出问题无法定位。

## 9. 未决问题

1. **480p 与 360p 的取舍**：640×480 在 15 fps 下必须 16bpp（9.2 MB/s），且 1.5× 非整数放大要额外做行对逻辑；640×360 可 24bpp + 2× 整数放大满屏。后者画质与实现都更优，前者分辨率标注更高。
2. **16bpp 值不值得**：引入 16bpp 解包（`bmp_pixel_unpack` 加一条通路，估 150–250 Slice）可把 SD 有效带宽翻倍，是 30 fps 高画质的唯一非硬件途径。但它要改 BMP 解析通路，会影响已签核的图片链路。
3. **SD 50 MHz 是否可救**：`SD_CLK_DIV_HS=1` 代码在，但真正卡点不是 `SAMPLE_DLY` 退化，而是 **`SD_CLK` 输出路径完全不进 STA、采样相位无可约束余量**——利用率 91.5% 时 `sd_card_clk` 域已有 14 setup + 7 hold 违例。若要把 50 MHz（25 MB/s）救回来，须先给 `SD_CLK` 输出加约束并把利用率压回 ≤85%，属板级/STA 专项。详见 §4.3。
4. **是否保留 AVI 容器**：保留的好处是"标准视频文件"叙事更硬、素材来源方便；成本是 media 多 ≈500–600 Slice。若评委看重"能直接放 AVI 文件"，这笔账要以面积换。

## 10. 修订方案：不删应急、保亮度（2026-10-29 13:15）

### 10.1 先澄清分工：视频逻辑在 media，不在 render

这一点容易误解，先把边界摆清：

| 环节 | 归属 | 与图片通路的差别 |
|---|---|---|
| 容器/帧解析 | **media** | 新增（图片走 BMP 头解析） |
| SD 读取 | **media** | 完全复用 `lba_stream` + `fat_chain_map` |
| 像素解包 / 打包 | **media** | 复用 `rgb888_word_packer` |
| 链路传输 | media→render | 复用图片通道 channel 2 |
| SDRAM 写入 | render | 复用帧写 FIFO 与仲裁 |
| 扫描输出 | render | 图片从两帧缓存读；视频可选独立区按行读 |

**media 干所有"把视频变成 720p 像素流"的活**，render 只负责显示。只有走独立扫描通路（§10.3）时 render 才加一个 `avi_scanout`；走图片事务（§10.2）时 render 一行视频逻辑都不加。现有分工完全不变。

### 10.2 路线 A：BMP 帧序列，复用现有 IMG 事务（推荐，0 删除）

利用两个现成事实：

1. `fat_bmp_controller` 已有 `action_next` / `key_next` 输入端口，脉冲一次就是"切下一张"，内部已处理目录推进、FAT 打开、缩放、打包、提交、`PRESENTED` 闭环。
2. `mix_transition_ctrl` 的状态机是 `T_IDLE→T_WAIT→T_FADE→T_FULL→T_RETIRE→T_REPORT`，`T_FADE` 就是那 30 帧淡化。加一个 DIRECT 分支：`T_WAIT` 在下一个 VS 直接跳 `T_FULL`，不做双读、不锁写缓存。

| 板 | 改动 | 估 Slice |
|---|---|---:|
| media | 帧节拍器：按 fps 分频，等 `img_idle` 后脉冲 `action_next`；与轮播/菜单/应急互锁 | 80–120 |
| render | `mix_transition_ctrl` 加 DIRECT 分支（跳过 T_FADE，VS 界直接换索引） | 60–100 |

资源核算：media 余量 264、render 余量 207，**两侧都够，不需要删除任何功能，DDC 都可以留着**（删它只是把时序余量换回来）。

| 项 | 结果 |
|---|---|
| 源分辨率 | 任意（复用 contain 缩放），480p/360p 自动放大到 1280×720 满屏 |
| 帧率上限 | **由链路决定**：每帧固定 2.76 MB → 15 fps 41 MB/s ✓、20 fps 55 ✓、25 fps 69 △、30 fps 83 ✗ |
| SD 需求 | 640×360 24bpp @15fps = 10.4 MB/s（**85%**，有余量）；480×360 = 7.8 ✓；320×240 = 3.5 ✓ |
| 音画同步 | 粗粒度：节拍由 media 固定，短片段可接受，长片段会漂 |
| 转场 | 帧序列期间必须 DIRECT；静态图片仍保留全部三种转场 |
| 限制 | 目录容量 256 项 → 15 fps 下最长 17 秒循环；每帧一次 FAT 打开（约 1–3 ms，占 66 ms 预算的 2–5%） |

**这是唯一"零删除、零 BRAM、零新格式"的方案**，代价是帧率上限 15–20 fps、没有逐帧时间戳同步。

### 10.3 路线 B：独立扫描通路（30 fps 唯一可行）

链路撑不住 30 fps × 2.76 MB（83 MB/s 贴顶），所以 30 fps 必须让链路只传源分辨率字节（320×240 = 230 KB/帧，30 fps 仅 6.9 MB/s），也就是回到 `avi_scanout` 那条路：视频帧写 SDRAM 尾部独立区，扫描器按行取、按行放大。

| 板 | 改动 | 代价 |
|---|---|---|
| media | 固定布局帧流解析（不做通用 AVI） | 300–400 Slice，**超过 264 余量，必须省** |
| render | `avi_scanout` + 仲裁接入 | 50–350 Slice + **1–2 块 BRAM32K（当前 0 空闲）** |

**render 的 BRAM：借台标的两块，播放期间隐藏台标。**
台标 `image_overlay_64` 占 2 块 BRAM32K，端口结构（A 口写入收图、B 口 `video_clk` 读出像素）与视频行缓冲**完全一致**，只是地址不同。加一组地址 MUX 和"视频播放中"模式位即可分时复用：视频播放时台标自动隐藏（这本来就是合理的 UI 行为），停播后恢复。成本约 50–80 Slice，零 BRAM 新增。这是分时复用而不是删除——台标在图片模式下照常显示，图层叠加叙事不受影响。

**media 的 300–400：换掉通用 AVI 解析。**
`avi_file_index` 是整个 RIFF 递归走查（240 行、4 级 rec 栈、1 个 BRAM32K、双流识别），远超演示所需。约定离线工具产出固定布局帧流（32 字节头 + 连续帧），这块整个不需要，`avi_player` 的三游标退化成单游标。

### 10.4 应急不能删，就把它身上的"假 DSP"还回来

读 RTL 发现一处明确浪费：`emergency_overlay` 的 `resource_emergency_dsp_pipe2` 是**两个 MULT18X18，B 端固定接 `18'd1`**，纯粹当两级延迟线用（源码注释："InputREG + OutputREG replace exactly the original first two stages"）。它占掉 2 个 DSP，而 render 的 DSP 是 29/29 满载。

同类"乘 1 延迟线"还有 `clock_overlay`(2)、`ui_text_overlay`(2)、`text_osd_overlay`(2)，合计约 **8 个 DSP** 在做移位寄存器的事。换回普通寄存器即可归还，零功能损失。

风险：这几处原本是为压时序才改成 DSP 的，换回寄存器必须重跑该路径时序；哪条反弹就只在那处保留 DSP。

另：`emergency_overlay` 自带 1 块字模 ROM（`resource_emergency_pair_rom`），可评估复用共享字库 `font_rom`。收益小、改动面大，放最后考虑。

### 10.5 修订后的结论

| 目标 | 方案 | 需删功能 | 需新 BRAM | 风险 |
|---|---|---|---|---|
| **15–20 fps，480p/360p** | 路线 A | **无** | 无 | 低。只动 media 节拍器 + render 直切分支 |
| 25 fps | 路线 A（贴链路顶） | 无 | 无 | 中。需实测 4 槽窗口能否维持 69 MB/s |
| **30 fps，320×240~480×300** | 路线 B | DDC（可选） | 借台标 2 块（分时） | 高。容器重写 + 仲裁时序 + 音画 PTS 重标定 |

建议先做路线 A 拿到"能演示的视频"，再评估是否值得为 30 fps 付路线 B 的代价。**路线 A 的改动是路线 B 的子集**（帧节拍器与 DIRECT 分支在路线 B 里同样要用），不存在返工。

唯一硬前置不变：**media 时序必须先闭合**（当前 −0.522 ns / 213 EP）。

## 11. 若 AVI 格式是硬要求（2026-10-29 13:22）

前提改为：系统面向通用，**必须支持 AVI 文件**，不能用 BMP 帧序列取巧。§10.2 路线 A 作废，改为"AVI 顺序播放器 + 现有帧事务"。

### 11.1 存档那版其实不通用，本来就要重写

`build/avi-v1/.../avi_file_index.v` 表面上做通用 RIFF 走查，实际把格式钉死在单一配置上：

```
if(incoming_word!=320) field_bad<=1;      // 只接受 320 宽
if(incoming_word!=240) field_bad<=1;      // 只接受 240 高
if(incoming_word!=32'h00180001)           // 只接受 24bpp BI_BGR
if(...!=rate25)                           // 只接受 25 fps
if(incoming_word>9320)                    // 帧数上限
```

所以它既不是"通用"的、还贵（media 超 722）。**目标既然通用，就不能照搬，得按"通用但要便宜"重写。**

### 11.2 便宜的通用：顺序流式 AVI，不要索引

那版贵在两件事，而这两件事对**顺序播放**都不是必需的：

| 存档里的机制 | 为什么要它 | 顺序播放时是否需要 |
|---|---|---|
| 第二遍扫 movi 建帧偏移索引（`SCAN`/`SCAN_CHUNK` 状态 + 两次扫描：视频一遍、音频一遍） | 支持随机访问、跳帧 | **不需要**。顺序播放只要"读下一块" |
| 4 级递归 `rec` 栈（`avi_rec_stack`，占 1 块 BRAM32K） | 跳过不关心的嵌套 LIST | **不需要**。顺序走查永远落在"下一块 = 当前 + 8 + 对齐后的长度"，不必知道父组多长 |

砍掉这两块，AVI 读取退化成：**头部走一遍（只走一条路径）+ movi 里逐块前进**。仍然能吃掉 ffmpeg 导出的各种未压缩 AVI，因为它对格式的适应性来自"按 chunk 长度前进"，而不是来自"预先建索引"。

### 11.3 与现有 BMP 通路的天然契合

未压缩 AVI 的视频帧就是 DIB：**BGR 排列、自下而上、行跨度 4 字节对齐**——和现有 `bmp_pixel_unpack` 的输入语义完全一致。而且常用宽度 320/480/640 的 `宽×3` 分别是 960/1440/1920，**本来就是 4 的倍数，行填充为零**。

所以复用关系是：

| 环节 | 复用情况 |
|---|---|
| 帧像素解包 | 直接复用 `bmp_pixel_unpack` |
| 等比缩放 / 补边 | 直接复用 `image_scale_geometry` + `image_scale_nearest` |
| 打包 / 链路 / 帧缓存 / 图层 / 字幕 | 全部不动 |
| 新增 | 只有"A VI 头解析 + chunk 顺序走查 + 按帧喂给现有解包器" |

### 11.4 新账

| 板 | 改动 | 估 Slice | 余量 |
|---|---|---:|---:|
| media | AVI 顺序器（头解析 + chunk 走查 + 帧游标，约 400–500 LUT） | **210–260** | 264 |
| render | `mix_transition_ctrl` 加 DIRECT 分支 | 60–100 | 207 |
| render | DDC/CI 删除（可选，换时序余量） | −290 | — |

**结论：15 fps 下塞得下，应急与亮度都保留。** 但这 210–260 是估算，必须综合验证；而且 media 时序未闭合前不能定案。

### 11.5 两条硬边界，必须先定

1. **压缩格式不可能。** 只能吃**未压缩 AVI**（`-c:v rawvideo -pix_fmt bgr24`）。MJPEG/DivX/Xvid 需要 JPEG/DCT 解码器：DSP 已 29/29 满、没有 BRAM 放 Huffman 表，直接否决。这条要写进系统的"支持格式"说明里。
2. **音频来源二选一。**
   - 用 AVI 内嵌 `auds` 流：更"通用"，但 chunk 走查要分辨 `00dc`/`01wb` 并做音视频双游标，media 侧多 150–200 LUT，264 的余量就不够了。
   - 用同名 WAV 配音：复用现有"图片同名 WAV 自动配音"机制，AVI 只当纯视频，解析器最小、余量够。
   建议先走后者，把"内嵌音频"作为后续增量。

### 11.6 30 fps 仍然要独立扫描通路

15 fps 是"每帧 2.76 MB 走链路"的天花板。要 30 fps 必须让链路只传源分辨率字节，回到 `avi_scanout`（§10.3），并借台标的两块 BRAM32K 分时复用。这条路的代价与风险见 §10.3、§7.1，不因 AVI 要求而改变。
