# B/C 应急接管首版（2026-10-13）

本版保留日常 BMP、目录枚举顺序、原背景音频控制、约 1 秒轮播间隔和原轮播开关。B 在任何页面进入应急；C 退出并恢复。协议为 1.8，两板必须配套更新。新增逻辑不缓存整段语音，不增加 GPIO 输入。

## 操作与素材

- SD 卡仍使用 FAT32，根目录放置 `EMERG.WAV`。名称大小写不敏感，必须完整匹配；`EMERG1.WAV` 不作为应急文件。开机枚举后记录文件位置，不支持运行中更换卡或修改目录。
- 文件格式与普通 WAV 相同：48 kHz、16 bit、PCM、单声道或立体声。该文件在浏览器中仍可见，但不加入普通“下一首”曲目表；其他文件顺序不变。
- B：黑底、固定向右的红色大箭头，约 800×400 像素、居中。无移动或闪烁。长按、松开后再次按 B 均不重启已处于应急状态的声音。
- 声音在 media 读取文件后启动，播放到实际消费曲尾时重新读取并循环；循环间允许短暂静音。应急数字增益固定 100%，原音量及其平滑状态保留，进入前静音不会关闭应急声音。
- C：停止应急音频，恢复进入前最后完整提交的图片和轮播开关；原背景音频从冻结的实际消费位置继续，保留暂停状态。无原音轨则恢复静音。恢复期间普通输入被屏蔽，B 可重新进入并保留最初的日常快照。
- 菜单关闭后不自动重开。文字、字幕配置、亮度、对比度和普通音量保留。应急期间屏蔽普通矩阵及板载操作，取消待切图与连发。

可用现有转换器准备音频：

```powershell
python tools/convert_fpga_wav.py "待转换音频.mp3" -o "EMERG.WAV" --ch 1
```

## 接管和恢复边界

render 独立读取 TM1650 驱动的 B/C 按下沿，不依赖普通键盘队列、菜单或网络。应急状态不随会话复位清除；render 系统复位会清除。视频输出增加一个统一 RGB/HS/VS/DE 寄存阶段，最高层在最终数字亮度之后覆盖，背景读取欠载、菜单及诊断不会遮住箭头。物理显示器的 DDC 亮度和显示器自身音量仍由显示器决定。

应急进入先本地冻结 PCM 消费，取得稳定的样本位置及图片快照，再通知 media。已经接受的图片事务可完成；新的 IMG_BEGIN 返回错误 `0x1004`，不能覆写保存图片。恢复先等待原图片事务完成 PRESENTED，再在帧界选择保存缓存，并等待读者交接；seam 同步更新图片标识后才释放保护。media 同时恢复文件游标，并刷新自动字幕关联。

WAV 通路复用原 FAT、段表、lba_stream、PCM FIFO 和播放环。重开原曲时先解析头，再按保存样本位置定位，目标 PCM_BEGIN 只发布一次，曲首样本不输出。更换或停止时等待实际 SD 流收尾；格式错误的残留字节不能进入新文件头解析。即使 SD 已读完、WAV 控制器空闲，停止也必须清除 render 尚未消费的样本。

恢复期间只预填原曲，不消费；画面和音频准备好后在 VS 消隐期间解除，下一活动帧恢复日常显示。原曲暂停时可完成预填并保持位置。复用原正常时钟及 HDMI 连续 48 kHz 节拍。

## 故障与状态

文件缺失、格式错误或读取失败保持箭头并停止声音，本次进入不无限重试；C 始终可退出。读取/恢复启动等待有 5 秒上限；原图片事务自身继续受既有看门狗限制。

断线时箭头保持、声音静音，重连后重新读取应急文件。断线中 C 可在帧界恢复本地图片，原音频等待重连；media 复位后不能凭旧音频快照报告完整恢复，退出后按原启动流程恢复。render 系统复位按原上电逻辑启动。

`DBG_EMERGENCY_MODE[1:0]`（render）和 `DBG_EMERGENCY_STATUS[7:0]`（两板）为 virtualIO，供调试/验收；mode 为 0 正常、1 应急、2 恢复。状态也通过可靠控制回复传输：

| 状态码 | 含义 |
|---|---|
| 0 | 初始正常 |
| 1 / 2 | 应急加载 / 应急播放 |
| 3 / 4 | 恢复中 / 原曲已建立目标流 |
| 5 | 无原音轨，恢复静音 |
| 6 / 7 / 8 | 应急文件缺失 / 格式错误 / 读取或等待失败 |
| 9 / 10 | 原快照不可用 / 原曲恢复失败 |

状态 4 后仍须等待本地预填及图片读者就绪才解除箭头；它不是已输出声音的确认。

## 自动验证与构建

```powershell
./tools/dual-board/run-emergency.ps1
./media/build/run.ps1 -Stage syn -RunTag emergency_peer -MapMode area_prior
./tools/dual-board/run-area-physical.ps1 -Board media -SynthesisRunTag emergency_peer -RunTag emergency_peer6 -PlaceSeed 6
./render/build/run.ps1 -Stage syn -RunTag emergency_cfg8 -MapMode area_prior
./tools/dual-board/run-area-physical.ps1 -Board render -SynthesisRunTag emergency_cfg8 -RunTag emergency_cfg5 -PlaceSeed 5
```

测试包括：921600 个应急像素与同步逐拍核对；本地键盘状态、冻结和帧界解除；真实 FAT32/双通道 SD 模型/生产 media_core/WAV/seam/PCM 的单声道、立体声、暂停、快速 B/C、重复 B、重入、无原音轨、缺失/格式/读取错误、断线和 media 复位；render 复位回到正常模式；两板独立可靠链路上的控制快照、丢包重传、图片保护与原图片/UI 事务。SD/PHY 电气、实体按键、SDRAM、HDMI 序列化及显示器声音均需实板验证。

保持既有资源和时序门槛及输入指纹。控制快照采用四个无负载的包头消息，避免将原可裁剪的发送/接收 RAM 扩展为完整 32 位缓存。恢复元数据占用既有目录 RAM 的保留区：普通目录仍是 0–255 共 256 项，地址 256–271 保存两张完整图片的描述、原音频文件/位置及四个音频 epoch 与文件的对应记录。独立综合确认 256×64 与 512×64 都是 4 块 BRAM9K；目录枚举和目录查找优先使用端口，图片加载期间可保存音频记录，恢复图片游标仍须等图片事务空闲。原音频恢复直接复用 WAV 的 pending-file 寄存器。预期 BRAM 仍为 media 56×9K+1×32K、render 51×9K+5×32K，最终结果必须以本轮物理报告为准。

实际消费 epoch 决定恢复文件，即使 media 已打开下一曲、render 尚在消费上一曲，仍恢复上一曲的冻结位置和暂停状态；恢复后同步普通下一首游标。目标流建立时清除旧 EOF 和预填标志，预填失败报告状态 10 并保持静音，不误用上一轮应急流的 ready 状态。

四条音频记录中，实际消费 epoch 对应的记录禁止被后续普通切歌覆盖。已经派发的 PCM_BEGIN 未得到 render 位置回报确认时，普通文件重开等待，最新请求仍保存在原 pending-file 寄存器中；防止长时间背压下连续切歌耗尽恢复记录。应急播放不受这个普通文件等待条件限制。冻结确认还等待 WAV 配置和 PCM 环清理交接完成，避免配置过程中的临时状态被误判为“无原音轨”。

`doc/dual-board/evidence/emergency-regression.json` 记录本轮测试数量、每份日志的 SHA256 和两板输入指纹。发布脚本要求完整回归指纹与当前源码一致，并再次验证资源、时序和 bit 校验值；未通过签核的 bit 不进入正式发布包。

当前 render 修正版已通过工具签核：`Runs/phy_emergency_cfg5`，Setup +0.101 ns、Hold +0.022 ns、TNS=0，51 BRAM9K + 5 BRAM32K，Slice 91.31%。media 正在筛选，以上 media 构建命令仅为当前构建流程，不表示该候选已经签核。旧 render `phy_emergency_release8` 不含配置交接修正，不作为本版交付。
